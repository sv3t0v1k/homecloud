# Политика безопасности HomeCloud v2

Дата: 2026-11-15.
Статус: ПРОЕКТ — G3.1.

Документ не является разрешением на публикацию,
установку обновления или отключение действующих gates.

## 1. Цель

Обеспечить безопасность HomeCloud без блокирования
развития продукта из-за неприменимых уязвимостей
внешних платформ и неиспользуемых инструментов.

Политика разделяет риски продукта, production runtime,
цепочки поставки и инфраструктуры CI.

## 2. Обязательные контуры

### PR / интеграция в test

- Backend unit, PostgreSQL integration, concurrency,
  filesystem, bench, frontend unit.
- Lint, TypeScript, build, configuration и Compose.
- Полное сканирование Git-истории на секреты.
- Авторизация, изоляция пользователей, безопасность
  файлов, хранилища, обновлений и восстановления.
- Recovery E2E до Merge, если изменение затрагивает
  хранение данных, backup, restore или их контракты.
- Независимый review критических изменений.

Неуспешная обязательная проверка блокирует Merge.

### TEST / приёмка кандидата

- Точные OCI-артефакты, SHA и platform digest.
- Native Linux/AMD64 и production runtime smoke.
- Backup, Restore, fault recovery, update и rollback.
- Проверка совместимости и целостности данных.
- Изолированное окружение и тестовые данные.

TEST не является подтверждением production readiness.

### RELEASE

- Утверждённый коммит main и неизменяемый тег v*.
- Положительная квалификация точного кандидата.
- Проверка production runtime и supply chain.
- Публикация квалифицированных OCI-артефактов
  без их неучтённой пересборки.
- Отдельный доверенный контур публикации.
- Отсутствие автоматической установки на сервер.

## 3. Классификация рисков

A. HomeCloud: дефекты авторизации, утечки, потеря
данных, обход границ доверия и security-регрессии
являются блокерами затронутого изменения.

B. Production dependencies: применимость CVE,
доступность исправления, путь эксплуатации и
компенсирующие меры оцениваются по точному артефакту.
Существенный неустранённый риск блокирует RELEASE.

C. Supply chain: нарушение доверенности источника,
целостности сборки, артефакта или публикации
является блокером. Уязвимости сборщика и инструментов
оцениваются по возможности повлиять на эти границы.

D. CI infrastructure: полный rootfs временного
GitHub runner и неиспользуемые системные компоненты
относятся к диагностическому контуру, если не
создают существенного риска для доверенной операции.

Глобальное требование 0 HIGH / 0 CRITICAL для всей
операционной системы временного runner отменяется
после реализации и проверки новой политики.

## 4. Секреты и исключения

Реальные и неразрешённые secret findings блокируют
Merge. Подтверждённые публичные ссылки могут быть
классифицированы как ложные срабатывания адресно.

Запрещены широкие исключения каталогов evidence,
отключение проверки истории и сокрытие findings.

Для индивидуального принятия риска необходимы
CVE, точная версия и digest, доказательства
применимости, компенсирующие меры, владелец,
срок действия и условие повторной проверки.

Ни одно конкретное CVE-исключение этим документом
не утверждается.

## 5. Fail-closed

Ошибка обязательного сканера, отсутствующие
обязательные доказательства, неверный target,
подмена SHA/digest и неизвестная целостность
артефакта не считаются PASS.

Статусы диагностики не подменяют результаты
обязательных продуктовых или release-проверок.

PR jobs не получают production secrets,
registry-write credentials или доступ к
production private network.

## 6. Миграция CI

Сохранить существующие продуктовые проверки.
Устранить повторное исполнение одинаковых тестов.
Отделить recovery от полной release qualification.
Перенести инфраструктурную диагностику в отдельный
контур с явными правилами оценки риска.

Required checks должны иметь уникальные имена.
Миграция branch protection выполняется после
проверки новых gates, без окна обхода защиты.

До завершения миграции действует существующая
политика docs/image-security-policy.md.

## 7. Текущие блокеры

- Gitleaks: требуется доказательная классификация
  всех неразрешённых срабатываний.
- PostgreSQL/gosu: отдельная runtime-оценка перед
  выпуском; существующий disposition INVALID.
- BuildKit: отдельная оценка build-time риска.
- CI environment: разделение диагностических
  findings и действительно используемых компонентов.
