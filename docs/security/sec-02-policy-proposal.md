# SEC-02 — согласованная архитектура безопасности

## Статус

Архитектура согласована владельцем проекта.
Действующие gates сохраняются до реализации и независимого review.
RELEASE остаётся NO_GO.
Конкретные CVE и существенные остаточные риски
не считаются автоматически принятыми.

## Цель

Безопасный и воспроизводимый выпуск HomeCloud.
Нулевое число findings во всей сторонней инфраструктуре
не является самостоятельной целью проекта.

## Обязательные контуры

### A. HomeCloud

Собственный код, зависимости приложения, backend/frontend runtime,
авторизация, файловое хранилище, установка и обновления.

Строгая блокирующая квалификация сохраняется.

### B. Сторонний production runtime

PostgreSQL, ingress и системные библиотеки.

Использовать поддерживаемые версии и точные digest.
Устранять доступные исправления.
Оценивать применимость и последствия оставшихся HIGH/CRITICAL.
Неизвестный или существенный неразрешённый риск блокирует выпуск.

### C. Цепочка сборки

BuildKit, инструменты CI, сканеры и окружение сборки.

Защищать целостность исходников, тестов, артефактов и credentials.
Предпочитать устранение проблемного компонента его исключению.
Сохранять точные hashes, provenance и исходные scan reports.

### D. Инфраструктура провайдера

GitHub-hosted Ubuntu 24.04 и подтверждённые provider-managed компоненты.

Использовать существующий механизм platform assurance.
Не переносить управляемые HomeCloud компоненты в этот контур
посредством простой переклассификации.
Неизвестная принадлежность остаётся блокером.

Инструменты и пакеты, самостоятельно установленные проектом,
не становятся provider-managed автоматически.

## Неизменяемые требования

- Ed25519 и целостность release-lock.
- Exact OCI digest и source binding.
- Provenance и квалификация фактических артефактов.
- Полнота отчётов и актуальность vulnerability DB.
- Проверка инструментов публикации до registry write.
- Сканирование секретов и полной Git-истории.
- Функциональные, интеграционные и recovery tests.
- Запрет скрытого подавления findings.
- Независимое review критических изменений.

## Порядок обработки рисков

Допускается группировка findings по общему компоненту,
причине и способу устранения.

Решение группы должно сохранять точный перечень входящих findings.
Отсутствие FixedVersion само по себе не разрешает выпуск.
NOT_AFFECTED требует проверяемого доказательства.
Существенный остаточный риск требует утверждения владельцем.

## Ограничение scope

Не создавать собственную универсальную систему управления CVE.
Использовать существующие сканеры, evidence и collector.

Новые улучшения, не препятствующие безопасности и выпуску,
переносятся в backlog.

## Порядок реализации

1. Восстановить provenance source contract.
2. Перевести backend CI на квалифицированное hosted окружение,
   сохранив непривилегированное выполнение тестов.
3. Квалифицировать PostgreSQL, BuildKit и CI tools.
4. Согласовать необходимые изменения правил допуска.
5. Провести независимое review и обязательный CI.
6. Выпустить следующий подписанный beta.
7. Завершить INS-05 на VM100.

Критерий завершения: фактический RELEASE lifecycle PASS,
а не только документ, коммит или зелёный CI.

# SEC-02 — проект политики квалификации безопасности

Статус: **ПРОЕКТ; RELEASE NO_GO**. Действует прежний gate до независимого
review, проверки реализации и отдельного утверждения владельцем. Этот документ
не разрешает публикацию или изменение severity.

## Основание и границы

Источник — точные JSON-артефакты [release run 46079544491](https://github.com/sv3t0v1k/homecloud/actions/runs/46079544491),
attempt 1, commit `92146048b570cc7c095abf919437196b648425e9`.
`scripts/ci/security-inventory.py` сохраняет report SHA256, идентификатор CVE,
пакет, установленную и указанную сканером исправленную версию, target и строку
исходного report. Наличие `FixedVersion` означает только запись в базе сканера:
доступность исправленного артефакта и его прохождение тестов проверяются отдельно.
Каждый raw report остаётся доступен как GitHub Actions artifact. Сводка не
заменяет исходный Trivy JSON.

В изученных обязательных jobs имеется 1084 блокирующих HIGH/CRITICAL записи
после исключения из этого **счётчика** уже диагностических host/raw-base
отчётов: 273 уникальных CVE. Это package findings, а не 1084 независимые
уязвимости. Разделение: production runtime PostgreSQL — 55; BuildKit — 142;
CI tools — 45; управляемая ОС двух backend CI containers — 490; смонтированные
инструменты платформы GitHub — 350; без надёжной атрибуции — 2. В host rootfs
сохранены ещё 4926 HIGH/CRITICAL, а в upstream-base diagnostics — 133; они
остаются видимыми, хотя не являются текущими блокерами. Остальные execution
environments должны быть проверены по полному coverage manifest до решения о
RELEASE.

## Пять контуров и решение по findings

| Контур | Владелец и воздействие | Обязательное решение |
|---|---|---|
| Production runtime | HomeCloud backend/frontend, ingress и PostgreSQL; сетевой ввод и пользовательские данные | Точный digest, linux/amd64, исходный report и runtime smoke. Исправить доступные CVE. Неизвестная применимость HIGH/CRITICAL блокирует. Для `not affected` требуется точное доказательство по binary/API; существенный остаточный риск — индивидуальное решение владельца. |
| Зависимости приложения | Установленные npm-пакеты backend/frontend, включая транзитивные | Скан фактического production artifact, путь от API/задачи к уязвимому коду и исправленная версия. Доступное исправление внедряется с regression tests. Необоснованное исключение блокирует. |
| Build environment | Фактические deps/builder stages, BuildKit и инструмент публикации | Целостность исходника, sandbox, provenance и точная привязка OCI остаются обязательными. Уязвимости, способные изменить выпускаемый артефакт или получить публикационные credentials, блокируют. Обновления проверяются по точному исполняемому образу; недоказанная достижимость не считается `not affected`. |
| CI tools | Gitleaks, Compose, Trivy, npm и другие фактически выполняемые инструменты | Полный scan и точный version/hash каждого исполняемого файла. Исправимые CVE устраняются. Неразрешённый путь атаки через PR, dependency, архив или сеть блокирует затронутый gate. Скан секретов и полная Git-история не отключаются. |
| GitHub infrastructure | Ephemeral Ubuntu runner, предоставленные GitHub actions runtime и toolcache | Полный raw rootfs scan, идентичность runner, DB freshness, источник и job binding сохраняются. Provider-managed код отделяется только при доказанном пути файла и владельце; неизвестная атрибуция остаётся блокером. В PR нет release signing secret, registry-write token или доступа к production network. В release publisher точные выполняемые инструменты и apt closure проходят отдельный строгий gate до login/write. |

Внутри backend CI container Debian OS — контролируемая среда, а не
`github-platform`: её 490 записей не переводятся в диагностику сменой имени.
Компоненты в `__t/` и `__e/` относятся к предоставленным GitHub mount только
после проверки точного пути; используемый actions runtime (`__e/`) также имеет
реальный supply-chain риск и требует pinned actions, минимальных permissions и
изоляции release job. Одна запись без пути остаётся `UNATTRIBUTED/BLOCKED`.

## Алгоритм принятия решения

1. Сначала проверяются полнота raw report, актуальность DB, SHA256, точный
   target/platform/source/run/attempt и связность с OCI или environment.
   Ошибка, пустой report либо неизвестный scanner status блокируют.
2. Каждая HIGH/CRITICAL запись получает домен, owner, package path, fix status,
   применимость к точному бинарнику, доступность уязвимого API, входной путь,
   возможный ущерб, компенсирующие меры и ссылку на первичный advisory.
   `UNVERIFIED` не превращается автоматически в PASS.
3. Исправление из upstream проверяется фактическим повторным scan, тестами и
   provenance. Только отсутствие finding в новом точном артефакте считается
   `FIXED`; обновление тега или версии без scan недостаточно.
4. `NOT_AFFECTED` допустим лишь для индивидуального CVE при совпадении
   digest/пакета/платформы и проверяемом доказательстве отсутствия затронутого
   кода или пути выполнения. Истечение срока, смена бинарника/DB/advisory или
   появление нового пути исполнения возвращает статус `UNVERIFIED/BLOCKED`.
5. `ACCEPTED_RISK` требует отдельного утверждения владельца для существенного
   остаточного риска: CVE, точный артефакт, сценарий эксплуатации, последствия,
   компенсирующие меры, срок и trigger повторного открытия. Широкие glob,
   игнор severity, удаление raw findings и выключение сканеров запрещены.

## Текущие технические работы

- Backend/frontend runtime, ingress и четыре build stage уже показывают ноль
  HIGH/CRITICAL в точных reports данного run; этот факт не переносится на
  PostgreSQL, BuildKit или будущее обновление.
- PostgreSQL имеет 26 Go stdlib findings в `gosu` и 29 OS package findings.
  Для точного `gosu` SHA256 `52c8749d…4b243dd0` выполнен новый binary
  `govulncheck`; первичная сверка 26 CVE с OSV показывает 25 отсутствующих
  affected packages и один пакет `os` без найденных affected symbols.
  Это кандидат на индивидуальную оценку, **не готовый disposition**.
  Истёкший disposition от 15 ноября не продлевается автоматически.
- BuildKit содержит 142 HIGH/CRITICAL package findings; новый upstream tag
  до фактического scan не считается исправлением.
- Gitleaks scan секретов завершился `PASS` с нулём неразрешённых находок; его
  собственный бинарник имеет 38 HIGH/CRITICAL findings. Compose имеет семь.
  Новые/пересобранные инструменты требуют source, hash, provenance, scan и
  контрактных тестов.
- В CI container 245 HIGH/CRITICAL на каждый из двух jobs относятся к Debian,
  175 — к GitHub mounts, одна запись без пути. У 239 Debian findings сканер
  не указывает исправленную версию. Переход на минимальный поддерживаемый
  container с нужными инструментами — исследуемый технический путь; host
  mounts не должны маскировать собственные OS findings.

## Условия утверждения и возобновления INS-05

Нужны завершённая индивидуальная классификация всех текущих блокеров,
исправления контролируемых компонентов, повторный точный CI, независимый
security review фактических diff и evidence, решение владельца по новой
политике и по каждому существенному остаточному риску. До этого RELEASE
остаётся `NO_GO`; тег `v0.9.0-beta.1` не переназначается. После утверждения
используется следующий свободный beta tag на новом MAIN commit и продолжается
эксплуатационная квалификация исключительно на VM100.
