# UPDATE UX: автоматическое закрытие результата TEST-установки

`current.json` остаётся единственным блокирующим статусом. Root-служба автоматически
архивирует только два подтверждённых результата: `INSTALLED/COMPLETE` в
`status/archive/<manifestSha256>.json` и `STOP/PREPARATION` в
`status/archive/<manifestSha256>-<16 hex от updatedAt>.json`. Второй результат
означает, что установщик отказал до создания `pending.json`; identity отклонённого
кандидата не заменяет identity предыдущего установленного checkpoint.

Перед архивацией сверяются `installed.json`, `last-status.json`, `state.json`,
отсутствие `pending.json` и `request.json`, а также работающие backend/frontend
контейнеры, их digest-pinned refs, image IDs, revision labels и состояние health.
Проверки выполняются под тем же `status/install.lock`, что и host installer.
Ошибка любого чтения, проверки, блокировки или синхронизации оставляет новое
обновление заблокированным.

Архивация использует долговечный `archiving.json`, жёсткую ссылку и `fsync`
файла и каталогов. Если питание пропало после удаления `current.json`, маркер
остаётся; backend показывает `UNKNOWN_REQUIRES_REVIEW`, admission отказывает.
Периодическая служба повторно проверяет все свидетельства и завершает переход.
Если обнаружен другой файл в архиве, неподтверждённый статус или дрейф образов,
автоматическая очистка не выполняется. Другие фазы `STOP` и
`MANUAL_RECOVERY_REQUIRED` никогда не архивируются автоматически. После проверенной
архивации `STOP/PREPARATION` UI получает `NO_JOB`, и администратор может явно
повторить установку после устранения причины отказа.

## Условия ввода на VM120 после PR и CI

1. До merge и независимого review не менять VM120, RELEASE или
   `AUTO_UPDATE=false`. Сам PR не устанавливает host-owned скрипт и unit-файлы.
2. Сверить точные байты принятого commit и отдельно переутвердить root-owned
   trust anchor `homecloud-update-verify`: его pinned hash admission изменился.
   Первая установка commit с изменениями `deploy` и `scripts` из текущей версии
   VM120 (`7a8eda9`) не пройдёт существующий `target_sources`, который требует
   идентичное дерево этих каталогов. Нужен отдельный проверенный переход доверия;
   нельзя обходить gate изменением checkout или копированием скриптов без
   квалификации. Пока переход не определён и не проверен, **UI E2E не принят**.
3. После разрешённого перехода установить `update-status-archive.py` как
   `/usr/local/sbin/homecloud-update-archive` (root:root, 0700) и новые
   systemd unit-файлы; проверить пути, ownership и effective sandbox. Включить
   постоянный приём явных UI-заявок и timer восстановления:
   `systemctl enable --now homecloud-update-admission.path homecloud-update-archive.timer`.
   Path не запускает обновление по расписанию: он реагирует только на заявку,
   опубликованную admin-only backend после проверки доступного кандидата.
   Отдельно проверить, что `COMPOSE_PROJECT_NAME` из защищённого
   `.runtime/runtime.env` совпадает с реально работающим проектом.
4. Проверить последовательные обновления через UI на TEST без открытия
   операторского окна по SSH: `QUEUED` → `RUNNING` → подтверждённый
   `INSTALLED/COMPLETE` → архив → `NO_JOB`. Сверить контейнеры, данные,
   миграции, backup, HTTPS и отсутствие `pending.json`/`request.json`.
   При любом несовпадении остановить сценарий, сохранить файлы и журналы для
   оператора. `AUTO_UPDATE` остаётся `false`: автоматического обновления по
   расписанию нет, admission path и archive timer остаются включёнными.
5. В E2E отдельно проверить безопасный отказ и восстановление доказательств:
   - `STOP/PREPARATION` → архивация прежнего checkpoint → `NO_JOB` → явный повтор;
   - два отказа одного кандидата → два разных архивных файла без перезаписи;
   - crash recovery suffixed STOP-архива после hardlink и после удаления
     `current.json`;
   - отказ после checkout, pull или stop → отсутствие кода `2`, автоматической
     архивации и повтора;
   - pending, symlink, повреждённые квитанции и неизвестный результат → сохранение
     блокировки.

Тесты в PR синтетические; они не подтверждают хостовый E2E или переход доверия.
