# Пользовательский канал обновлений — дизайн

Статус: предложение к обсуждению (2026-11-18).
Ответственный: чат тимлида. Согласование: владелец проекта.

## 1. Проблема

Механизм обновлений проекта сегодня состоит из двух разных по зрелости частей:

- **TEST-канал (стенд VM120)** — полный цикл «проверка → установка → откат»
  (`deploy/linux/update-*.py`, host-якоря в `/usr/local/sbin/`).
  Но каждое изменение охраняемых helper-файлов требует ручной
  квалификации: хост доверяет конкретным байтам, а не цепочке подписей.
- **RELEASE-канал (пользовательский)** — бэкенд (`updates.service.ts`)
  только **показывает**, что доступна новая версия. Автоматической
  установки у пользователя нет: релизный lock проверяется, подписи нет,
  установщика на хосте пользователя не существует.

Требование владельца: любой пользователь должен уметь и установить
проект, и обновить его, без участия ИИ или «оператора с ssh».

## 2. Принципы

1. Хост доверяет **ключу**, а не байтам. Ключ меняется раз в годы
   (ротация), а не на каждый релиз.
2. Каждый релиз **подписан**. Проверка подписи заменяет ручную сверку
   хэшей helper-деревьев для пользовательских установок.
3. Установка обновления **атомарна и обратима**: новый слот →
   health-проверки → переключение → автоматический откат при провале.
4. Стенд VM120 **не облегчается**. Его строгий trust gate остаётся —
   это песочница, которая ловит баги класса «дискриминатор среды»
   (прецедент f175185 / PR #56) и защищает от вредоносного кандидата.
   Пользовательский канал — отдельный путь доставки.
5. Ошибки fail-closed и говорящие: нет подписи / нет сети → «проверка
   недоступна», никогда молчаливый пропуск.

## 3. Целевая схема

```
CI (release.yml)
  └─ релиз vX.Y.Z[-beta.N]
       ├─ release-lock.json        (уже есть: образы, миграции, provenance)
       ├─ release-lock.json.sig    (НОВОЕ: подпись приватным ключом релиза)
       └─ update-bundle/           (helper-скрипты установщика, хэши)

Хост пользователя
  ├─ bootstrap (первичная установка):
  │    установщик ставит root-якорь = ПУБЛИЧНЫЙ КЛЮЧ (+ URL канала)
  └─ обновление (по кнопке в UI / таймеру):
       1. скачать release-lock.json + .sig, проверить подпись ключом
       2. сверить provenance образов и дайджесты (логика из updates.service.ts)
       3. записать новые helper-скрипты во второй слот
       4. применить обновление, прогнать health-gate (миграции + smoke)
       5. успех → переключить слот; провал → откат на прежний слот
```

### 3.1 Формат подписи

Предлагается минимальный, проверяемый offline вариант:
Ed25519, публичный ключ зашит в установщике, приватный — в GitHub
Secrets с публикацией подписи в релизе. Альтернатива — Sigstore/cosign
keyless (прозрачность, но зависимость от их инфраструктуры и онлайна).
Решение фиксируется до Этапа 1 (см. п. 6).

### 3.2 Двухслотовые helper'ы

Текущая модель «один якорь с зашитыми хэшами» заменяется на:
`helpers/A/`, `helpers/B/`, указатель `active` (root-owned, 0600).
Обновление пишет неактивный слот, проверяет, переключает указатель.
Откат = указатель обратно. Слот перезаписывается только после успеха.

### 3.3 Совместимость миграций

Текущее правило exact-migrations (одинаковый набор миграций) сохраняется
на переходный период: оно предотвращает пропуск обязательных миграций
при перепрыгивании версий. Отдельным решением позже — цепочка
миграций (накат с прогоном всех промежуточных), когда появится
инструментарий её проверки в CI.

## 4. Этапы внедрения

| Этап | Содержание | Что разблокирует |
|------|-----------|------------------|
| 1 | Подпись релизов в `release.yml`; публичный ключ в репо; проверка подписи в `updates.service.ts` (available показывается только для подписанных релизов) | Пользователь перестаёт доверять неподписанным релизам |
| 2 | Установщик пользователя: bootstrap-скрипт + root-якорь-ключ + двухслотовые helper'ы + верификатор подписи (отдельный репозиторий или `deploy/user/`) | Первичная установка любым пользователем |
| 3 | Применение обновления по кнопке в UI: скачивание бандла, слот B, health-gate, откат; отчёт в UI | Обновление в одно действие |
| 4 | Процедура ротации ключей (два ключа, overlap-период, команда в UI) | Долгоживущая безопасность |

Каждый этап — отдельные PR и отдельное review. Этапы 1 и 2 можно
вести параллельно. Текущий TEST-канал и стенд на всех этапах
продолжают работать без изменений.

## 5. Что происходит с текущим кодом

- `deploy/linux/update-*.py`, `test-channel.py` — остаются стендовым
  каналом; их trust gate не трогаем. Правки багов (например,
  дискриминатор среды) продолжают идти батчами через доверенный переход.
- `updates.service.ts` — расширяется проверкой подписи (Этап 1);
  retry/версионный модуль — уже в PR #60.
- `scripts/ci/release.py` — добавляет генерацию `.sig` (Этап 1);
  расширение формата тега за пределы `v0.X.Y-beta.N` — совместимо
  с уже влитым модулем версий.
