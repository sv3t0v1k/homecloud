# Phase 3.1 — isolated installer E2E stand plan

No stand is provisioned and no installation is authorized by this plan. Use a separate Linux/amd64 machine or VM, never the mini-PC or production volumes.

## VM feasibility against the existing gates

`deploy/linux/preflight.py` accepts native `x86_64`, local rootful Linux Docker without rootless/userns/Desktop, at least 7 GiB `MemTotal` and 2 GiB `MemAvailable`. The dedicated disk mode requires **two distinct** `/dev` block-device ancestry chains containing only `part` and `disk`, exact ext4/xfs mount points, UUID, configured serial and WWN, no nested data mounts, and separate filesystem UUIDs. The startup gate additionally compares `/dev/disk/by-uuid`, host and container mountinfo, bind identity, markers and ownership. Loop files, ordinary directories, tmpfs and GitHub-hosted runner storage do not establish this contract.

A VM with two exclusively assigned virtual block devices **might pass the implemented checks** if its hypervisor exposes stable, distinct serial/WWN and the guest reports the required ancestry and mount data. This is conditional on a read-only preflight and startup-gate inspection; it is not proof of physical device independence. The source comments and operational documentation describe physical disks. If physical separation is an acceptance requirement, use an isolated bare-metal host or pass through two dedicated physical devices. Do not remove or spoof a check to make a VM pass.

Minimum preflight resources: 8 GiB nominal RAM (the actual `MemTotal` check is 7 GiB) with 2 GiB available before start; two dedicated ext4/xfs filesystems; positive configured free-space and inode budgets. The example inventory uses **10 GiB free for DB** and **20 GiB free for storage**, each with 10,000 free inodes. E2E sizing must additionally hold two full backups, restore scratch space, images and logs; these example floors alone are not a sufficient backup budget. The backup verifier creates a 1 GiB network-isolated tmpfs PostgreSQL and is limited to 512 MiB RAM. Reserve a distinct Compose project/network, test HTTPS hostname or IP with trusted test certificate, and no routes or mounts to live HomeCloud data.

## Qualification sequence

1. Record read-only `findmnt`, `lsblk`, `/dev/disk/by-uuid`, Docker architecture/security, memory and capacity evidence. Confirm two independent device identifiers and project-only paths before creating any data. Obtain the owner's decision on whether a virtual-disk VM counts as an operational E2E stand.
2. Provision a root-owned checkout and fixed verifier/worker anchors only after separate review of their exact bytes. Keep `PROVISIONED=False`, the bridge flag false, and invoke the installer directly through the trusted test wrapper for qualification. Prepare isolated runtime/recovery env, markers, startup gates, PostgreSQL and file storage with synthetic rows/files, real Compose images and test HTTPS. Use `baseline-inspect`; adopt its initial checkpoint only after matching live image IDs/refs, Git revision, migration names and an explicit operator decision.
3. Choose two protected TEST commits with the **same `deploy` and `scripts` trees**, changed application image digests, and either identical migration inventories or a strictly additive target. Confirm both artifact/provenance pairs. A transition from `40f11e2` to `b6ddfbd` cannot serve as the successful case because the helper trees differ. Any trusted helper change requires a separate review and root-owned anchor replacement before a new qualification campaign.
4. Record starting rows, file SHA256, container image IDs/refs, migrations and checkpoint. Run real `test-channel.py apply`: verify trust and compatibility, execute `backup.sh` and the existing backup verifier, switch with no-build Compose, check backend/frontend and public HTTPS, then compare final data and durable checkpoint. For an additive target, record `MIGRATION_APPLY` after the verified backup and before `START_SERVICES`; only `db` and the new `backend` may start in that phase. Preserve raw evidence outside the test data volume.
5. On disposable resets, inject refusal before backup, backup corruption, failure after stop, migration mismatch, an unapplicable new migration, backend/frontend or HTTPS failure, SIGKILL during `MIGRATION_APPLY`, timeout/lost success acknowledgement, and repeated apply. For each, record phase/pending/last-status, containers, migrations, rows and file SHA256. A migration-phase failure or SIGKILL must yield `MANUAL_RECOVERY_REQUIRED`, retain `pending.json`, and block another apply until `recovery-inspect` and operator reconciliation. Perform documented manual rollback/restore only when its verified backup and journal support it; compare every data set after recovery. No `ROLLED_BACK` verdict follows from container restart alone.

The installer accepts an exact migration inventory or a strictly additive target. Before a transaction, applied names must exactly equal the installed checkpoint; every installed `{name,file,sha256}` entry must remain unchanged in the target. Removal, replacement, rename, source modification, and applied drift refuse before backup. After `BACKUP` and `WRITE_REFS`, `MIGRATION_APPLY` starts only `db` and the new `backend`: its entrypoint executes TypeORM `migration:run --transaction all` before the API. The installer verifies the backend image and requires `sorted(applied_migrations()) == migration_names(manifest)` before `START_SERVICES`, then repeats the exact inventory check after full startup. Backup validation intentionally continues to use the old active checkpoint because the backup predates migrations. Migration rollback is **restore from the verified backup only**, never a down-migration or automatic container restart.

This contract change does not itself prove real migration execution. A separately reviewed trusted transition and real drills for successful 31→34 apply, unapplicable migration, SIGKILL during `MIGRATION_APPLY`, and blocked retry remain required before claiming Operational E2E. Likewise, the worker remains blocked by `PROVISIONED=False`; direct installer qualification does not authorize enabling it.

Decisions required before provisioning: whether virtual disks satisfy the acceptance goal or physical devices are mandatory; the isolated host and two disk identities/capacities; the initial and target protected TEST commits with unchanged helper trees and an exact or additive migration relation; who approves initial checkpoint adoption and root-anchor changes; and the permitted failure/restore window. Until those are settled, **Operational E2E: BLOCKED**.
