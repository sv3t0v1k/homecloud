# Первоначальная настройка администратора HomeCloud

Операторский bootstrap — локальная операция владельца сервера.
Она не доступна через HTTP API.

## Предварительные условия

- Используется установленная и утверждённая версия HomeCloud.
- PostgreSQL работает, все миграции текущего образа уже применены.
- Backend API остановлен, чтобы освободить эксклюзивную блокировку
  storage root.
- Для production используются те же Compose-файлы, env-file и project,
  что при штатном запуске установленной системы.
- Startup gate, storage root fence и maintenance inhibitor сохраняются.

Не используйте --entrypoint, --privileged, произвольные команды
из контейнера или подмену DATABASE_URL для обхода ограничений.
Не удаляйте maintenance.inhibit ради bootstrap.

## Новая установка

На пустой таблице пользователей:

```sh
docker compose stop backend

docker compose run --rm --no-deps backend \
  node dist/users/admin-bootstrap-cli.js bootstrap create \
  --email owner@example.com --name "Administrator"
```

Пароль вводится дважды в интерактивном терминале без отображения.
Минимум 12 символов, максимум 72 байта UTF-8.
Не передавайте пароль через argv, env-file, переменные окружения,
историю команд, перенаправление stdin или постоянные файлы.

Начальная квота администратора равна нулю. Данные пользователя,
файлы и квоты других аккаунтов не затрагиваются.

## Существующая установка

Если в базе уже есть пользователи, выбирается существующий активный
аккаунт. Оператор обязан самостоятельно подтвердить принадлежность
этого аккаунта владельцу сервера.

```sh
docker compose stop backend

docker compose run --rm --no-deps backend \
  node dist/users/admin-bootstrap-cli.js bootstrap promote \
  --user-id 1 --email owner@example.com
```

ID и канонический email должны соответствовать одной записи.
Пароль, имя и квота сохраняются. Роль повышается до ADMIN,
старые access и refresh сессии отзываются атомарно.

## Результат и повторный запуск

Успех возвращает JSON с полями status, userId, email, role.

Статус already-configured означает, что выбранный аккаунт уже является
активным администратором. Пароль и версия сессии не изменяются.

Если существует другой активный ADMIN, bootstrap отказывает.
После запуска API управление другими пользователями выполняется в разделе
«Настройки HomeCloud» → «Пользователи» или через защищённый Admin API.

## Завершение операции

После успешного bootstrap:

```sh
docker compose up -d backend
```

Проверьте штатный healthcheck и вход выбранного администратора.
После повышения существующего аккаунта требуется повторный вход.

На production добавляйте фактические параметры Compose установленного
стека ко всем приведённым командам; не создавайте новый project.

При BOOTSTRAP_SCHEMA_NOT_READY не запускайте произвольные миграции.
Сначала проверьте версию установленного образа, резервную копию и
штатную процедуру обновления. Bootstrap никогда не меняет схему.

При отказе root fence проверьте, остановлен ли API. Не обходите
блокировку. При ошибке maintenance gate используйте предусмотренную
процедуру операторского обслуживания и восстановления.

Публичная регистрация отключена: `POST /api/v1/auth/register`
возвращает HTTP 403 с кодом `REGISTRATION_DISABLED` для запросов,
дошедших до контроллера.

Первоначальная настройка ADMIN и отказ публичной регистрации
проверены на production-образе Linux ARM64 с установленным
startup gate, настоящей PostgreSQL и интерактивным TTY.

Admin API и интерфейс поддерживают создание, редактирование, смену пароля,
точные квоты в байтах, блокировку, реактивацию и удаление пользователей.
Последний активный администратор защищён от понижения, блокировки и удаления.
Удаление с незавершённым восстановлением, активными copy-операциями или
pending/uploading legacy-сессиями отклоняется. Физические пути сохраняются в
`user_deletion_operations` в той же транзакции, что и удаление аккаунта.
При `cleanupPending: true` запись журнала остаётся: повторный DELETE или
запуск backend возобновляет очистку. Журнал удаляется только после успешной
физической очистки; ответ с `cleanupPending: true` нельзя считать завершением.
Постоянный административный audit trail и invalidate при восстановлении
резервной копии остаются отдельными этапами.
