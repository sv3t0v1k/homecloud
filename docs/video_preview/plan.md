## 1. Цель и границы

### 1.1 Цель
Реализовать генерацию и отображение видеопревью — один извлечённый кадр из видеофайла в виде статичного изображения (PNG), наравне с существующей поддержкой изображений и текстовых файлов. Решение одобрено владельцем проекта: «превью для видео (1 кадр как картинка)».

### 1.2 В scope
- Добавление системной зависимости `ffmpeg` только в Docker-образ backend (не nginx, не frontend).
- Расширение `PreviewsService` (backend): новый тип `video` в ответе API `/previews/:id`, возвращающий один PNG-кадр.
- Расширение `PreviewsController`: аутентифицированный доступ к видеопревью, те же guards, что у существующих превью.
- Расширение фронтенда: тип `PreviewPayload` получает вариант `video`; `PreviewModal` отрисовывает `` (тэг img) для извлечённого кадра, а не `<video>`.
- Лимиты: только видео до 5 MiB (существующая граница превью), один кадр на видео, формат PNG.
- Тесты: unit, integration, lint, typecheck, build — по правилу 7 AGENTS.md.
- Документация: обновление README.md (раздел «Превью и миниатюры») и ROADMAP.md (снятие ограничения «новые preview formats» из Out of scope Phase 13.5).

### 1.3 Out of scope
- Воспроизведение полного видеофайла в браузере (видеоплеер) — отдельная функция, не превью.
- Элемент `<video>` с контролами, `muted`, `poster`, временной шкалой — превью отображается как статичное изображение.
- Извлечение нескольких кадров, анимированных GIF.
- Видеопревью для публичных ссылок без аутентификации (только authenticated, как существующие превью).
- Новые номера Phase — задача остаётся в бэклоге без новой фазы.
- Изменение существующего поведения для изображений и текста.

### 1.4 Критические ограничения (по AGENTS.md)
- Не начинать реализацию без прямого указания владельца проекта (Правило 2). Согласие получено 2026-11-21.

## 2. Текущее состояние (базовая линия)

### 2.1 Backend
- `backend/src/previews/previews.service.ts` — поддерживает только `image/*` (sharp, 300×300 PNG) и `text/*`. Видео попадает в `type: "unsupported"`.
- `backend/src/previews/previews.controller.ts` — `GET /previews/:id` с JwtGuard, возвращает `PreviewPayload`.
- `backend/src/entities/file.entity.ts` — поле `mimeType` (строка до 100), нет отдельного поля типа превью.
- `ffmpeg` не используется нигде (grep — ноль совпадений).

### 2.2 Фронтенд

- `frontend/src/files/thumbnailApi.ts`, `thumbnailQueue.ts` — только для миниатюр изображений.

### 2.3 Инфраструктура

- `docker-compose.production.yml`, `docker-compose.yml` — нет ffmpeg-контейнера или зависимости.

## 3. Архитектурное решение

### 3.1 Общий принцип
Видеопревью = один извлечённый кадр из видео в формате PNG, размером не более 5 MiB, генерируемый бэкендом через `ffmpeg` при первом запросе и кэшируемый на диске. Фронтенд отображает кадр как `` (не `<video>`).

### 3.2 Backend

#### 3.2.1 Новая зависимость
- Добавить `ffmpeg` только в `Dockerfile` backend.
- Не добавлять в nginx-образ и не добавлять в frontend.
- Закрепить версию `ffmpeg` в Dockerfile (pin версии) для воспроизводимости сборок.

#### 3.2.2 PreviewsService
Добавить метод `generateVideoPreview(fileId: string, storagePath: string): Promise<PreviewPayload>`:
1. Проверить, что файл существует и `mimeType` начинается с `video/`.
2. Проверить размер файла ≤ 5 MiB (существующая граница превью).
3. Проверить MIME-тип по allowlist поддерживаемых контейнеров (mp4, webm, mov) и magic bytes файла (не только расширение).
4. Вызвать `ffmpeg` через `execFile`/`spawn` с массивом аргументов (не строка), флаги: `-nostdin -hide_banner -loglevel error -threads 1`, тайм-аут 30 секунд, `-ss 00:00:01` до `-i` (fast seek), `-frames:v 1 -f image2 -` для извлечения первого кадра в stdout.
5. Ограничить размер stdout/stderr (например, 10 MiB), запуск от непривилегированного пользователя, изоляция temp-каталога.
6. Для видео короче 1 секунды: fallback seek к позиции 0.
7. Проверить размер извлечённого кадра ≤ 5 MiB.
8. Вернуть `{ type: 'video', content: Buffer (PNG), mimeType: 'image/png' }` — клиент отображает как ``.
9. Кэшировать результат в существующем хранилище превью (если есть) или временном каталоге с TTL и инвалидацией при удалении исходного файла.

#### 3.2.3 PreviewsController
- Маршрут `GET /previews/:id` уже существует. Расширить логику: если `mimeType` видео — Delegating к `generateVideoPreview`.
- JwtGuard остаётся без изменений.
- `Cache-Control: private, max-age=86400` + `Vary: Authorization` (как у существующих превью, см. ROADMAP 11.3).

#### 3.2.4 FileEntity / DTO
- Нет необходимости в новых полях БД: тип определяется из `mimeType`.
- Если потребуется хранение ссылки на сгенерированное превью — добавить поле `previewPath`nullable в отдельной миграции (решение на этапе ревью).

### 3.3 Фронтенд

#### 3.3.1 preview.ts
- Расширить тип `PreviewPayload` вариантом:
  ```ts
  | { type: 'video'; content: { type: 'Buffer'; data: number[] }; mimeType: string }
  ```
- Функция `previewImageBlob` остаётся для изображений; добавить универсальную `previewMediaBlob` для создания `Blob` из видеокадра (PNG).

#### 3.3.2 PreviewModal.tsx
- Для `preview.type === 'video'` отрисовать `` с `src={objectUrl}` и `alt`.
- Обработка `onLoad`/`onError` аналогично изображению.
- Освобождение `objectUrl` при размонтировании (уже реализовано в cleanup effect).

#### 3.3.3 Тесты
- `preview.test.tsx` — добавить кейс для `type: 'video'`.
- `PreviewModal.test.tsx` (если существует) — добавить рендеринг `` для видео-превью.

## 6. Безопасность

### 6.1 Риски ffmpeg
- `ffmpeg` — большая поверхность атаки (много форматов, кодеков, уязвимости в парсерах).
- Митигация: ограничить входные файлы только теми, что загружены через существующий pipeline upload (уже проверенные MIME, размер).
- Не передавать пользовательский ввод напрямую в аргументы `ffmpeg` — только файловый путь из контролируемого хранилища.
- Запускать `ffmpeg` с тайм-аутом (30 секунд) и ограничением вывода (stdout/stderr ≤ 10 MiB).
- Флаги безопасности: `-nostdin -hide_banner -loglevel error -threads 1`.
- Запуск от непривилегированного пользователя, изоляция temp-каталога.
- Валидация MIME по allowlist (mp4, webm, mov) и проверка magic bytes файла.
- Pin версии `ffmpeg` в Dockerfile.

### 6.2 Аутентификация и авторизация
- Видеопревью доступно только аутентифицированным пользователям (JwtGuard, как у всех превью).
- Доступ только к собственным файлам (проверка `userId` в `FileEntity`).

### 6.3 Кэширование
- `Cache-Control: private, max-age=86400` + `Vary: Authorization` — нет публичного кэширования (ROADMAP 11.3).
- Стратегия инвалидации: кэш превью инвалидируется при удалении исходного видеофайла; TTL для устаревших записей.

## 7. Ограничения и деferred решения

- Видео > 5 MiB — превью не генерируется, возвращается `unsupported` (как сейчас).
- Только один кадр (первый, по времени 1 секунда; fallback к 0 для коротких видео). Анимированные превью — out of scope.
- Нет отдельного хранилища превью — используется временное/кеш хранилище, очищаемое по TTL.
- Публичные ссылки (sharing) — видеопревью не доступно анонимно.
